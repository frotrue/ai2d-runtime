# v0.6 implementation plan — bounded content foundations

## Objective

Version 0.6 adds five reusable content foundations without turning the runtime into a general-purpose engine:

1. deterministic sprite clip animation;
2. compile-time prefab expansion;
3. versioned bounded save slots;
4. bounded tile layers and integer fields;
5. a narrow commercial baseline: input profiles with gamepad bindings, camera rigs, anchored/stack UI and localization, streamed PCM WAV music, and preallocated particles.

GameManifest/SceneSpec 0.2 through 0.5 remain supported and retain their source and plan hashes. New data is accepted only by GameManifest/SceneSpec 0.6. The project version becomes 0.6.0.

## Design constraints

- Every authored name used by a fixed tick is compiled to a numeric index.
- Every runtime collection has an authored or compile-time capacity and is reserved during initialization or scene load.
- Prefabs are data-only, non-recursive, and fully expanded by the compiler. They do not exist at runtime.
- Animation, camera, tile/field, particle, and input-profile updates do not allocate or grow containers during fixed ticks.
- Save-file and music-stream I/O are structural work. A fixed tick only records a bounded request; the runtime performs it immediately after that completed tick and before the next tick.
- No scripting, arbitrary expressions, runtime component registration, runtime entity creation, generic asset importer, animation graph, or general UI tree is introduced.

## Public 0.6 contract

### Manifest additions

- `prefabs`: zero to 256 `{id,path}` entries referencing `prefab-v1` JSON.
- `animations`: zero to 512 sprite clips. Each clip references one PNG and has 1–256 frames, each with a normalized UV rectangle and a 1–1,000,000 tick duration. Playback is `once`, `loop`, or `ping_pong`.
- `localizations`: zero to 32 `{locale,path}` entries referencing `localization-v1` JSON. Keys are identical and ordered identically across locales; `default_locale` is required when the array is non-empty.
- `input_profiles`: one to 16 profiles. Each logical action can bind up to four keyboard keys, four gamepad buttons, and two signed gamepad axes with a finite deadzone in `(0,0.95]`.
- `save`: optional bounded configuration with 1–16 slots and an explicit list of persistent integer states. Scene/world snapshots are saved only for scenes marked `persistent`.
- `music` assets are streamable PCM or IEEE-float WAV files. They are not decoded into the resident startup audio set.

### Prefabs

`prefab-v1` contains one optional transform, velocity, sprite, collider, and initial animation. A 0.6 spawn group may name one prefab and override any component as a whole. Prefabs cannot include groups, children, pools, systems, rules, or other prefabs. Expansion occurs before normal component, capacity, and ownership validation.

### Animation

- A prefab or spawn group may declare an initial clip and `autoplay`.
- `play_animation` targets a group, fixed index, contact A/B, or animation event entity; it names a clip and optionally restarts it.
- `stop_animation` freezes the current frame.
- `animation_finished` fires once for `once` clips in entity order. Its entity is exposed as `event_entity` to the matching ordered actions.
- Pool reset/acquire restores the group's authored animation state. Scene snapshots retain clip, frame, phase, direction, and playing/completed flags.

### Tile layers and integer fields

- A scene has zero to 64 tile layers and zero to 64 integer fields.
- Each references an existing logical grid and therefore has at most 1,000,000 cells. Total tile plus field cells are capped at 4,000,000 per scene and across the complete game.
- A tile layer references a PNG atlas, an atlas grid, initial tile IDs or a fill value, a render layer, tint, and visibility. Tile ID 0 is empty.
- An integer field declares `min`, `max`, and an initial value or full initial array.
- Conditions read a constant cell or the cell containing a fixed/contact/event target.
- Ordered actions `set_tile`, `set_field`, and `add_field` mutate one resolved cell. Out-of-grid target resolution reports failure through an optional result state and never indexes storage.
- `game verify` observes tile and field values through precompiled numeric targets.

### Save runtime

- Ordered actions `save_slot`, `load_slot`, and `delete_slot` use a constant authored slot and optional result state.
- Only one save request may be pending. It executes outside `fixed_tick`, immediately after the tick that emitted it. Batched and one-at-a-time exact-tick execution therefore observe the same boundary state.
- The binary header contains magic, format version, exact plan hash, payload length, and checksum. A mismatch rejects the complete load; no partial or best-effort migration occurs. The compiler computes the exact worst-case encoded size and rejects plans above the 64 MiB save-buffer limit.
- Writes use an isolated per-writer sibling temporary file and atomic replacement. Loading validates the complete payload, bounded counters, and derived invariants into preallocated scratch before mutating live state.
- Saved data includes declared integer states, current scene, global simulation tick, persistent scene snapshots and their scene ticks, pool/contact/animation/camera/particle/tile/field state, locale, and input profile.
- Save capacity is calculated during initialization and capped at 64 MiB per slot.

### Commercial baseline

- `camera.mode` is `fixed` or `follow`. Follow names one fixed spawn index plus offset and optional center bounds. Optional pixel snapping and seed-derived tick shake are deterministic; zoom is bounded to `[0.1,10]`.
- UI elements may use one of nine anchors. Positions consistently denote element centers. A bounded stack contains declared child IDs and resolves their centered positions at compile time using direction, padding, and spacing. It is not a retained widget tree.
- Text uses either literal `text` or localized `text_key`. `set_locale` and `set_input_profile` accept compiled constants.
- Input profiles aggregate logical action state across keyboard, mouse, gamepad buttons, and signed axes. Only aggregate state transitions emit edges, and profile changes synthesize semantic release edges for bindings that disappear at the next fixed-tick boundary, including inside batched execution.
- Music actions are `play_music`, `stop_music`, and `set_music_volume`. One stream is active, looping is explicit, fades are tick bounded, and a fixed 32,768-frame stereo-float ring is filled outside simulation ticks.
- A scene has at most 64 particle emitters, each with 1–10,000 preallocated slots; aggregate capacity is 100,000 per scene and across the complete game. `emit_particles` emits a bounded constant count at a constant or target position. Exhaustion is `skip` or `recycle_oldest`. A reserved minimum heap and intrusive active queue avoid capacity-wide emission scans. Particles are presentation-only and never collide.

## Diagnostics and metrics

New authoring diagnostics are `GAME_ANIMATION_INVALID`, `GAME_PREFAB_INVALID`, `GAME_SAVE_INVALID`, `GAME_TILE_FIELD_INVALID`, `GAME_INPUT_PROFILE_INVALID`, `GAME_LOCALIZATION_INVALID`, and `GAME_PRESENTATION_INVALID`. Corrupt runtime/save invariants use `RUNTIME_ANIMATION_STATE_INVALID`, `RUNTIME_SAVE_STATE_INVALID`, and `RUNTIME_TILE_FIELD_STATE_INVALID`.

Metrics include animation frame updates/completions, tile/field reads and writes, save attempts/successes/failures/bytes, camera follow/shake updates, particle emits/updates/exhaustions/slot operations/peak active, music stream bytes/underruns, input-profile switches, and localized text resolutions.

## Implementation phases and validation

1. **Compiler contract** — schemas, plan values, strict parser rejection, public-plan revalidation, 0.6-only hashing, dependency inspection, and legacy-hash regression tests.
2. **Animation and prefab slice** — component/snapshot/pool integration, ordered actions/events, source-free sample, and allocation tests.
3. **Tile/field and save slice** — fixed storage, numeric observations, binary round-trip, corruption, atomicity, and exact tick-boundary tests.
4. **Commercial baseline slice** — input profiles/gamepad, camera, compile-time UI layout/localization, music streaming, and particles.
5. **Tooling and content** — inspect output, package dependencies, repeat-isolated temporary save slots, one 0.6 declarative sample, and `game verify` scripts.
6. **Closure** — Debug, Release, ASan, GPU-off, Vulkan/synchronization validation, shader validation, architecture, benchmark, fresh ZIP extraction, and GPT Pro review.

## Explicit exclusions

- skeletal or blend-tree animation;
- recursive or runtime prefabs;
- arbitrary serialization, save migration, or reflection;
- chunk streaming, infinite maps, autotiling, tile collision baking, or fluid/heat simulation;
- arbitrary input-capture UI or unbounded user binding lists;
- runtime UI reflow based on text measurement;
- compressed music codecs or a general audio graph;
- particle collision, GPU particles, lighting, materials, or post-processing;
- pathfinding, task AI, networking, 3D, editor, and hot reload.

## Definition of done

- All five foundations work together in a declarative 0.6 sample with zero game-specific C++.
- New success paths and authoring failures have automated coverage and structured metrics.
- Existing 0.2–0.5 samples retain their pinned source/plan hashes.
- Fixed-tick animation/tile/field/camera/particle work shows zero tracked project allocation and zero capacity growth after warm-up.
- All available build, test, validation, package, and extracted-player gates pass; unavailable checks are recorded honestly.
- GPT Pro reviews architectural fit and correctness; every finding is revalidated locally and every confirmed defect is fixed and retested.
